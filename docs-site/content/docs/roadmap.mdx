Versions, not dates. A dated roadmap ages whether or not anything changes; a version says what a release will contain and nothing about when it ships.

Anything listed under a version is being built. Anything under **Exploring** is not committed to a release, and **Not planned** means what it says — those entries exist so you do not build on something that will never arrive.

## Available now — v0.8.9

**Typed human queries.** An agent asks with a closed answer shape — `boolean`, `choice`, `scalar`, `date`, `text` or `fields` — and gets a structured answer back rather than prose to interpret. An admission gate refuses a question a human could not decide, with a `remedy` field telling the agent what to add.

**MCP server.** `human_query`, `get_query`, `list_queries`, `clarify_query`, `cancel_query`, over OAuth. Works with Claude and any MCP client.

**REST API for agents**, with WebSocket and webhooks for delivery. Webhook
deliveries follow [Standard Webhooks](https://www.standardwebhooks.com): the
signed content covers the timestamp, so a captured delivery cannot be replayed,
and a rotation signs with both the old and the new secret for 24 hours so it
never drops a delivery. Verify with `verifyWebhook` from
`@agentdialog/sdk/webhooks`, or any off-the-shelf implementation.

A webhook has to point somewhere public. A URL that resolves to loopback, to a
private range, or to a cloud metadata address is refused with `422` when you
register it and again before every delivery, and a redirect is never followed —
register the final destination. This is what stops one tenant's webhook being
used to probe the network the API runs in.

**TypeScript SDK** on npm as `@agentdialog/sdk`, with adapters for LangChain (`/langchain`) and the Vercel AI SDK (`/ai`).

**A web chat for humans.** They answer there — no account to create, no
password.

**One-click answers for low-risk questions.** A `low` or `medium` risk query is
mailed a link that opens that one question and resolves it, with no sign-in at
all. The link is a capability scoped to a single query: whoever holds it can
answer that question and nothing else — not read the conversation, not see other
queries, not reach the account. `high` and `critical` mint no such link; there
the email carries a sign-in code, as before.

**Idempotency keys.** Send `Idempotency-Key` on a POST and a repeat of it returns
the original response instead of doing the work twice. Seven routes honour it —
the four that create something a person sees, plus webhook creation and the two
rotations. Only successful responses are remembered, so a `422` from the
admission gate leaves the key free for the corrected retry. The TypeScript SDK
sends one on every write and keeps it across its own retry, so an integrator gets
this without writing anything.

**Emails in the language you declare.** A query can carry `language`: `en`, `es`
or `ca`. It changes the wrapper the product puts around your question — the
subject line, the labels, the dates — and it does **not** translate your words.
The question, the subject, the options and their consequences are sent exactly as
you wrote them, so write them in the language you declare. The sign-in code email
is the exception that proves the rule: it follows the browser of whoever asked
for it, because that person is looking at a screen when they ask.

**File attachments** in conversations.

## v0.9

### A LangGraph-native integration

The LangChain adapter already works inside a LangGraph graph, because it exposes ordinary tools: `ask_human` and `check_answer`. But that shape is polling. The agent asks, then calls back to see whether an answer has arrived, and burns a model call each time it does.

LangGraph has a better primitive for this. `interrupt()` suspends a graph and a checkpointer resumes it with the human's value, so waiting costs nothing. Mapping a query onto interrupt and resume is what makes AgentDialog idiomatic there rather than merely usable.

### An answer that reaches the agent, instead of the agent asking again

An MCP client cannot receive a webhook. It is not an HTTP server, and nothing on our side pushes into an MCP session, so an agent running in Claude — or in any other MCP client — finds out that a human answered only by calling `get_query` again. It works, and the answer is there when it looks. But the agent has to decide to look, and every look is a model call spent on "not yet".

What closes it is a tool that waits: ask about a query and block until the human answers or the wait runs out. The server already knows the instant an answer lands, because it publishes it to Redis for the chat's live updates. Waiting means subscribing to that, not asking the database over and over.

It cannot wait indefinitely — a client will time out a request long before a person necessarily answers — so the tool returns *still open* and the agent calls again. That is one call per minute of waiting rather than one per guess. It is also the same primitive the LangGraph work above needs: something that knows the exact moment to resume.

### The Python SDK, brought up to date and published

`sdks/python` exists and is not published. It also predates typed queries: it covers conversations, messages, invitations and webhooks, and has no query support at all — the product's central primitive is missing from it.

Publishing it is therefore not a packaging task. Parity first, then PyPI.

### A document the human can actually open

A query carries text and only text: the subject body, the context, the question. An agent that wants a person to look at a PDF has two ways to do it today and neither is good — paste the extracted text into `context`, which is capped at 100,000 characters and arrives as a wall of prose, or host the file somewhere itself and point at it with `subject.uri`.

Attachments do exist in the product, but they hang off messages rather than queries, and a file download is scoped to the conversation that holds it — which is exactly what the holder of a one-click answer link is not part of. So this is not a matter of wiring up an endpoint that already exists: it needs a file that belongs to a query, and a download a grant can authorise without widening what a grant means.

One thing it will not do is put the document in the email. Mail is forwarded, archived and synced through places nobody here controls; the capability link is the boundary, and the file belongs behind it.

### An abandoned `needs_context` query expires

When a human replies that they lack the context to decide, the query returns to the agent as `needs_context` and its clock pauses. If the agent never clarifies, that pause has no ceiling and the query stays open with its deadline sliding into the past.

No data is lost, and the rows are harmless. But an agent cannot currently distinguish *paused* from *abandoned*, and it should.

## v1.0

**Queries that need more than one human.** One question, several people, one settled answer. A direct extension of the typed-query model rather than a new one.

**Delegation between agents.** Handing a conversation from one agent to another with its context intact, so the human sees a continuation instead of a fresh stranger.

## Exploring

Not committed to a release. Listed because they are real questions, not because they are scheduled.

**An agent directory** — discovery by capability, with public profiles.

**Reputation** — humans rating the agents that interrupt them.

**A2H compatibility** — a translation layer for the Agent-to-Human protocol, which depends on a standard we do not control.

## Not planned

### Reading inbound email

**A reply to a notification email is not read, and that is a decision.** Email tells a human there is a question and carries their sign-in code. They answer in the web chat.

The alternative was built and measured before being rejected. Polling a shared mailbox makes the `\Seen` flag mean two incompatible things at once — *a person read this* and *the system processed this* — so any reply someone opened first was lost silently. And mail addressed to other people is never marked read, so the unread backlog was re-downloaded in full on every pass.

Underneath both: a shared mailbox is not a queue, and treating it as one fails quietly rather than loudly.

If a transactional provider is ever configured on our own domain, the webhook that would receive it already exists and verifies signatures. That is configuration, not construction — but it is not on this roadmap.
